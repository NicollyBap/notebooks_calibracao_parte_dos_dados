Build specification · Projeto Nicolly

Tumor Fit Tool

A local app where a researcher uploads their own tumour volume data. It fits the growth laws, picks the best one, fits the treatment term on top, and then lets them simulate dosing protocols to plan the next experiment.

01What exists and what is missing

The scientific code already works, but only if you edit Python. Today you rename the files to match a fixed convention, run 28 notebook cells, read the winner from a text file, copy the model and its parameters by hand into a second notebook, then run again.

Saving those steps is not the real gain. The gain is being able to ask what if: take a model fitted on real data and try a dosing schedule nobody has run at the bench yet.

Nothing in the scientific core gets rewritten. The seven laws, the multistart fit, the metrics and the validation all move out of the notebooks into modules, unchanged.

02How to build it

Seven stages, holding everything the first working version needs. E0 comes first and everything else depends on it. E1 and E2 can be built at the same time, since one is the server and the other the interface, and they meet at E3. After that the order is fixed, because each tab needs what the previous one produced.

Before the first line of code

The project has no requirements.txt, and the .venv/ in the folder is broken. It was copied from another project and carries JupyterLab but not numpy, scipy, pandas or matplotlib. Delete it, make a fresh one, and write the requirements: numpy pandas scipy matplotlib openpyxl fastapi uvicorn python-multipart pydantic pytest.

03Getting the data in

This is the part that decides whether the tool is usable. Today the data must be renamed to fit the code. Here the code adapts to the data, and the user is the one who says what each column means. Everything downstream assumes the shape produced at the end of this path, so build it first and build it carefully.

Do not assume a regular grid

Times can be non-integer, subjects can start at different days, and the number of points differs from animal to animal. Nothing downstream may assume a uniform step, a common start time, or an equal count per subject. This falls out naturally if step 6 keeps one independent table per animal.

05What is being fitted

A one-variable ODE for the tumour volume T(t), with a growth term and an elimination term:

dT/dt = G(T) − C(t, T) · T
        ↑ growth law      ↑ treatment effect

Order matters. Fit G(T) on the control group first, where C is zero, then fit C(t,T) on the treated group with G(T) frozen. Fitting both at once makes the problem ill-posed, because growth and elimination trade off against each other.

The seven growth laws, in growth_term(t, T, params, model). exponential has a closed form and skips the integrator.
LawdT/dtPar.Behaviour
exponentialr·TrUnbounded growth.
mendelsohnr·Tbr, bPower law, b<1 slows down.
logisticr·T·(1 − T/K)r, KSaturates at K, symmetric.
bertalanffyr·T2/3 − α·Tr, αSurface gain, volume loss.
gompertzr·T·ln(K/(T+c))r, K, cSaturates asymmetrically.
linearr·T/(T+f)r, fTends to a constant rate.
surfacer·T/(T+f)1/3r, fBetween linear and exponential.

For the treatment term, each dose d given on day τ contributes from τ onwards, with Δt = t − τ and D the cumulative dose. Only ED is written today. The other five already have their formula in section 7.1 of the treatment notebook and just need to become code.

All of them sum over the doses and return C ≥ 0. none is the baseline and must always be in the comparison.
NamePer dosePar.Biological reading
none0n/aBaseline.
EDa·d·e−b·Δta, bEffect fades after the dose.
CDa·D·e−b·Δta, bDriven by cumulative dose.
AccelEDa·d·e−b·Δt²a, bShort window of action.
MMa·d/(1 + b·d)a, bDoubling the dose does not double the effect.
LSa·d/(1 + b·T)a, bA larger tumour resists more.
dePRδ·dλ/(s·Tλ + dλ)δ, s, λDose competes with tumour size.

When porting dePR, rename the parameter d to delta. In the original formula it clashes with the dose, also called d.

One fit for the whole group

The law is shared across the group, but each animal gets its own initial volume, since the mice share the biology and not the implant size:

θ = [ r, K (shared) | T0₁, T0₂, …, T0ₙ (one per mouse) ]
k_total = n_shared + n_mice

The objective is the mean SSE, with a 1e18 penalty when integration fails. The optimiser is L-BFGS-B with multistart, N starts sampled inside the bounds and the best one wins. Several of these models have local minima, so multistart is not optional.

Picking a model

  • BIC is the main criterion, and ΔBIC against the winner is what the user actually needs to see. Below 2 counts as a tie.
  • Akaike weights turn those gaps into something that reads like a relative probability, which is the clearest way to show a tie to someone who is not a statistician.
  • Last-point validation refits without the final points and measures the error on them. It tells apart a model that describes the data from one that predicts, which is what matters when planning an experiment.

06Architecture and API

Local and offline. A Python server on 127.0.0.1 serves the interface as static files and exposes a JSON API, so the data never leaves the machine.

No bundler and no framework. Native ES modules and plain CSS. Calibration takes minutes, so it runs in a queue with one worker thread while the frontend polls progress every 500 ms. Use threads rather than processes: SciPy releases the GIL in the numeric work, this is a single user on one machine, and the shared_to_params lambdas cannot be pickled.

The session carries the winning growth law, and the server rejects a growth that contradicts it, so tab 5 can never simulate a model tab 3 did not pin.

07Pitfalls and settled decisions

T0 sits on its bound for nearly every mouse

Every digitised trajectory starts at the same floor value, which is an artefact of reading points off a graph rather than a measurement, and the bounds are [0.10·v₀, 4·v₀]. So most fitted T0 values end up sitting on a bound, which means the optimiser wanted to go further and could not.

So the app puts the T0 mode and its bound fractions in tab 2, and shows the boundary warnings in tab 3, instead of burying them in a text file.

The winner changes with the settings

The same group can pick a different law depending on the T0 bounds, and the gap to the runner-up is often under 2 BIC units. An interface that announces one best model and says nothing about the rest would be misleading.

Multistart is not optional

Several of the laws have local minima, so with too few starts the result changes between runs and the winner can flip. That is why the seed is a visible field, it goes into the provenance record, and the fast preset says out loud that it is for exploring rather than for a final answer.

Settled decisions

  • Python backendThe SciPy core is already validated. Rewriting the ODEs in another language risks diverging from results already reported, with nothing gained.
  • No frontend frameworkES modules and plain CSS. A local offline app does not need a build chain.
  • Local and offlineUnpublished data stay on the machine, and nothing is fetched at runtime. The charting library is vendored.
  • Growth before treatmentG(T) comes from the control group and enters the treated fit frozen. Fitting both together makes the problem ill-posed.
  • The notebooks stayThey are not deleted. They remain as teaching material, running on the same extracted core.

Out of scope for now

Written down so it does not creep in: parameter sweeps with sliders, automatic outcomes such as time to doubling or survival, sample size calculation, and uncertainty bands from a parametric bootstrap. That last one is the best candidate for the next version and already has a working implementation under old/.
